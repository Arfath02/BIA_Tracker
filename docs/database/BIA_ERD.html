Project planning and progress

The task parent FK includes projectId, so SQL rejects a parent from another project. Subtasks use the same tasks table. Predecessor edges use a separate junction table. Task department is derived through projects.

Identity, department access and audit

Users belong to one department and one fixed application role. Department membership plus explicit project grants determine visibility. Management is the read-only role with portfolio-wide access. Password hashes are separated from user profiles. Authorization is enforced by the API; these tables do not grant end users direct SQL access.

Purchasing and settlements

Current workflow: one full settlement per invoice; no partial payments. Paid/Unpaid is derived from the settlement row. Project-currency amounts use decimal precision; USD reporting uses project rates. The API checks cumulative PO commitments against the project budget and cumulative invoices against the PO in a transaction.

Operational metadata

These tables intentionally have no business foreign keys. workspace holds only a version counter, never project data. schema_migrations records installed schema versions. login_attempts stores hashed throttle keys and expiration times.

Design notes

Nullable master primary departments are retained only for older masters awaiting correction; the API requires a valid department for new or edited masters. Historical unknown user IDs remain null rather than being inferred from names. Audit actor names and progress author names are intentional historical snapshots.
